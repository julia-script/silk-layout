# silk-layout

MIT-licensed block and flexbox layout in safe Silk, with specification-derived algorithms and a replaceable measurement provider. **Full CSS conformance is the target, not the current verified status.** See [standards, coverage gaps and license provenance](SPECIFICATIONS.md).

## Build and check

The workspace pins published Silk `0.1.0-dev.26+430d979004dc`. Use an LLVM 22 clang; set `SILK_CLANG` to its absolute path if it is not automatically discovered. On Linux x86_64, `export SILK_CLANG=$(scripts/install-llvm)` downloads the official LLVM 22.1.8 release and keeps only clang under `.cache/`.

```sh
silk toolchain install 0.1.0-dev.26+430d979004dc
scripts/check
silk build --package silk_layout_cli
python3 scripts/fetch-specs.py
```

Chrome source-text comparisons additionally need the MIT-licensed FontTools build tool:

```sh
python3 -m venv .cache/font-tools
.cache/font-tools/bin/python -m pip install fonttools==4.67.0
```

The oracle uses that interpreter automatically; `SILK_FONT_PYTHON` selects another installation. Native layout and spec checks do not depend on Python font tooling.

`layout/` is the library; `cli/` is a native JSON adapter used by the conformance and benchmark scripts. The package exports `layout.lib`. Source-tree ownership, node handles and result storage are separate; layout borrows the input tree and writes into a reusable `LayoutTree`.

## Incremental layout

A `LayoutTree` keeps size results between `compute` calls on the same `Tree`, keyed by generated box and the exact constraints that produced them (like taffy's and Yoga's node caches). `Tree` methods that change content (`setStyle`, `setText`, `setMeasurement`, `setNaturalMeasurement`) advance `Tree.revision()` and record it on the node; the next compute clears the results of that node's boxes, their descendants, and their ancestors, and reuses the rest. Code that edits `Tree.nodes` or `Tree.styles` directly must call `Tree.markDirty(node)`. Final layout is reused too, like Blink LayoutNG's and Servo's layout result caches: an independent formatting context (the root, flex items, block-level formatting-context roots, atomic inlines) whose subtree is unchanged and whose layout request equals the previous compute's gets a copy of that compute's fragments and box records instead of a layout. So does an in-flow block child that shares its parent's formatting context, when its subtree has no floats or negative margins and the floats reaching below the top of its content box sit where they did relative to it, since then its layout depends only on its request and those floats. Subtrees containing out-of-flow boxes or inline interruptions are always laid out, because positioning completes them. A compute with no change since the last one, the same viewport and the same scroll offsets returns at once, and generated boxes are rebuilt only when a change can alter them (an insertion, a measurement, `markDirty`, or a style change to `display`, `position`, `float`, `writingMode`, `alignContent`, `overflow` or `replaced`). When generated boxes do change (an insertion, or a `display` change), kept results move to the matching new boxes: a sourced box matches the same continuation of its source, an anonymous box the alike anonymous child of its matched parent. Boxes without a match, or whose fields or children differ, are laid out again with their ancestors. Auto scrollbars and fragmented layout fall back to a full layout. Results depend on the measurement provider: call `LayoutTree.invalidate()` after replacing it, after its answers change, or before computing a different `Tree` with the same output. `LayoutTree.stats` reports the last compute's passes, full layouts, size probes, cache hits and reused subtrees.

## Display and measurement

`Style.display` separates how a box participates in its parent from how it lays out descendants:

```silk
style.display = Display.Box {
  outside: DisplayOutside.Inline,
  inside: DisplayInside.Flex
}
```

`Display.None` suppresses a subtree; `Display.Contents` suppresses only its principal box. Neither carries meaningless outer/inner fields. A `Contents` layout root contributes its descendants directly to the supplied viewport, without applying its own box styles. CSS spellings such as `inline-flex` and `inline flex` are normalized by the adapter. Blockification changes the outer type without changing flex layout; the CSS-defined `inline flow-root` exception becomes `block flow`.

Source elements, source text, generated boxes, and physical fragments have separate identities. `Tree.appendText(parent, value)` takes ownership of a UTF-8 `String`; text nodes share their parent's source-style slot rather than carrying a full `Style`. Element styles live in `Tree.styles`, addressed by `Node.styleIndex`. Text nodes cannot own children, measurements, or scroll state. Box construction flattens `contents`, blockifies flex items/floats/positioned boxes, creates anonymous inline-formatting runs, groups adjacent flex text into anonymous items, and splits inline ancestors around in-flow blocks. `LayoutTree.getBox(BoxId)` addresses generated sizing results; `firstBox(NodeId)` locates a source's first generated box. A source can have no box or several continuations. `fragments` retains individual box/inline/text/line geometry rather than replacing fragmented inlines with a bounding rectangle.

Inline fitting items hold compact geometry and an index into an atomic-leaf arena. Only atomic boxes and floats retain child layout requests, measured sizes, margins, and float positions; opening/closing inline scopes and static anchors do not carry unused full `Layout` records.

`Measure.font(provider, FontRequest)` supplies font size, ascent/descent, line gap, x-height/cap-height, script offsets, and baseline-table offsets. The request includes `key`, writing mode, text orientation, and used direction; `Style.fontKey` selects the key. The engine uses these metrics for inline struts and vertical alignment; it does not embed a font backend. `Layout.hasFirstBaseline` and `hasLastBaseline` are independent; the opaque `Measured.hasBaseline` response still supplies joint availability.

`BaselineSet` retains alphabetic, ideographic, central, mathematical, x-middle, text-over, and text-under positions. `FontMetrics.baselines` uses the font content-over edge; `Measured.firstBaselines`/`lastBaselines` use content block-start; `Layout` and `Fragment` sets use their own box's block-start. Translation and axis reversal preserve the whole table. Baseline alignment selects the receiving context's baseline type rather than reusing the child's dominant baseline; `middle`, `text-top`, and `text-bottom` select their corresponding entries. `forContext(writingMode, textOrientation)` selects central for vertical mixed/upright text and alphabetic otherwise. Upright `middle` alignment selects central rather than x-middle.

`Style.textOrientation` accepts `Mixed`, `Upright`, and `Sideways`. In vertical-rl/lr, upright forces `Style.usedDirection()` to LTR for layout, while leaving the computed `direction` unchanged for inheritance. Horizontal-tb and sideways writing modes are unaffected. Both font and opaque-content measurement requests carry text orientation and used direction; providers remain responsible for orientation-dependent text metrics and shaping.

Implement `Measure` and `TextMeasure` on the provider passed to `compute`. `Measure.measure(&mut provider, key, request)` supplies opaque content measurements: known dimensions are content-box dimensions, and available spaces distinguish definite, min-content and max-content requests. Its response supplies content size and optional first/last baselines, measured along the node's logical block axis from content block-start. `natural(&mut provider, key)` supplies a resource's independent optional width, optional height, and natural aspect ratio; a missing dimension is not zero. Attach opaque content with `Tree.setMeasurement`, or a replaced resource with `Tree.setNaturalMeasurement`. The engine owns CSS sizing and adds padding/border. Replacing the provider requires no tree rewrite, but kept results (see [Incremental layout](#incremental-layout)) still reflect the old one: call `LayoutTree.invalidate()` after replacing a provider or changing what it returns, or `Tree.markDirty(node)` when only one node's content changed.

`Measured.contentBlockSize` reports the unaligned flow extent in the logical block axis, separately from the constrained `Measured.size`. For example, ten pixels of text inside a fifty-pixel-tall content box still reports a ten-pixel flow extent. The engine uses it for block `align-content`, including safe overflow and vertical writing modes. `Layout.measurementOffset` is the physical translation to apply when painting externally measured content; ordinary child boxes already contain their alignment displacement and must not receive it again. Output baselines already include this translation. The JSON adapter exposes it as `measurementOffsetX` and `measurementOffsetY`.

`Measured.hasLineBoxes` distinguishes absent inline content from a zero-height line that still separates margins; missing baselines are not evidence that a block is empty. Ignore phantom lines as required by CSS 2.1 §9.4.2. The fixture adapter defaults this field to `true`; `"hasLineBoxes": false` requires zero intrinsic metrics and no supplied baselines, and the Chrome oracle emits no inline content for that case.

`Measured.scrollableOverflow` reports the external content's scrollable, not ink, overflow as a physical content-box-relative `Rect` before block content alignment. Its coordinates may be signed; its dimensions must be nonnegative. Known dimensions constrain `Measured.size` but must not erase overflowing text or displaced lines. The engine adds box insets and the physical measurement alignment offset.

The request borrows the current float-exclusion context for the measurement call. `request.lineSpace(inlineSize, blockOffset, lineBlockSize)` returns the available `lineLeft`/`lineRight` interval in logical line-left/block-start coordinates relative to the content box. If a line cannot fit a `constrained` interval, retry at `nextBlockOffset`; `exclusionBlockEnd()` marks where preceding floats cease affecting subsequent lines. The provider owns shaping and line breaking, and includes any displaced lines in its content extent and baselines. These queries neither copy the float list nor expose mutable layout state.

Provider caches must not reuse line-layout results solely by measurement key and dimensions: the borrowed float exclusions and content origin can differ between requests.

`TextMeasure` is the composable source-text boundary, separate from opaque content measurement. `beginTextLayout` starts each compute; `analyze` supplies ordered Unicode break opportunities and returns paragraph analysis; `shape` measures a requested candidate line with the complete surrounding paragraph and immutable analysis still available. The engine owns whitespace normalization, CSS wrap restrictions, line selection, float fitting, baseline placement, and fragment construction. It reshapes candidate ranges rather than assuming contextual advances are additive. To keep that affordable, unfragmented left-to-right paragraphs without floats, tabs, preserved spaces or hyphenation shape once in full, use the summed advances only to guess each line's last fitting break, and then shape the guessed line and its neighbors exactly; line advances must grow as content is added. Within one compute, a paragraph's min-content and max-content widths and the break points chosen for each line width are remembered while its items and inline edges are unchanged, so further probes of the box at the same width shape only the lines they keep. Without a visual plan or tabs a range's shaping does not depend on where its line starts, so each shaped range of a paragraph (a candidate line, a min-content segment, the whole paragraph) is remembered, up to about two per break opportunity, and copied when a later probe, line or compute covers it again. These per-paragraph results, with the paragraph's text analysis, are kept between computes until a change reaches the box, so a resize neither analyzes nor reshapes unchanged text it has already fitted. After fitting a justified line, `TextShapeRequest.justificationSpace` requests additional advance from the provider's eligible opportunities, without changing content coverage or vertical metrics. Unexpandable lines use the CSS `text-align-last` fallback; forced breaks also trigger last-line alignment.

`Style.textJustify` selects `Auto`, `None`, `InterWord`, or `InterCharacter`. Tokens carry their own computed method, and `TextContext.textJustify` supplies the root inline method for nearest-common-ancestor boundary decisions. The engine supplies `TextShapeRequest.hangingRanges` from the selected line's visual geometry, including decoration fences and conditional versus unconditional hanging; providers exclude those ranges from expansion. Inter-character spacing follows visual bidi order and is shared between adjacent units, without adding spacing at line edges. Consecutive atomic inlines form one spacing unit. `TextRun.Object.lineLeftSpacing` and `lineRightSpacing` carry finite nonnegative expansion outside the atomic margin box in visual line-relative axes; they do not change the object's intrinsic size or used margins.

`Style.textIndent` contains a length/percentage `Dimension` plus `hanging` and `eachLine` flags. The engine applies it as a line-start margin before fitting and alignment, using the block container's own inline size for percentages, including beside floats. Generated inline runs retain first-formatted-line ownership across intervening block children. Forced breaks and soft wraps select different lines under `eachLine`; `hanging` reverses that selection. Intrinsic contributions resolve the percentage component against zero, retaining the length component.

`TextContext` borrows tokens and their source strings independently. Text tokens retain source UTF-8 offsets, font keys, writing mode, orientation, direction, whitespace-collapse policy, and shaping barriers; inline scopes, atomic objects, floats, and static anchors remain separate tokens. Cursor offsets address UTF-8 bytes for `Text` and ASCII bytes for `PreservedSpace` runs, one virtual unit for `Space`, `Tab`, `SegmentBreak`, or an atomic object, and zero units for structural markers. Preserved spaces are borrowed in runs where their breaking policy permits, rather than allocating a token and fragment per space. The end cursor is `{unit: tokens.length, offset: 0}`. Providers append logical-order, source-attributed runs to caller-cleared reusable lists. Text runs must cover the requested scalar-aligned ranges exactly; atomic runs identify their token. Providers shape tabs and segment breaks as covering zero-advance text runs: the engine supplies tab-stop geometry and forced-line layout. `TextError` reports unsupported measurements or malformed provider ranges.

`Style.whiteSpaceCollapse` separates Collapse, Discard, Preserve, PreserveBreaks, PreserveSpaces, and BreakSpaces from `textWrap`. `tabSize` is a nonnegative `TabSize.Number` or `TabSize.Length`; its default is eight measured spaces. `FontMetrics.spaceAdvance` and `zeroAdvance` are replaceable-service measurements of U+0020 and U+0030, not font-size estimates. Tab stops use the nearest block container's space advance and the half-`ch` clearance rule. Preserved trailing spaces retain paint geometry while hanging widths are excluded from line fitting; conditional hanging affects only the overflowing portion for alignment and is included in max-content, but not min-content, sizing.

`TextContext.unicodeBidi` carries the originating block's non-inherited paragraph policy. Scope tokens carry their own `unicodeBidi`; `replacedInline` distinguishes inline replaced content from ordinary neutral atomic objects. `Style.unicodeBidi` and the CLI's `unicodeBidi` accept normal, embed, isolate, bidi-override, isolate-override, and plaintext. The analysis service interprets CSS-generated controls without changing source offsets; ordinary empty scopes, floats, and anchors do not become neutral text characters.

`TextAnalysis.uniform(units, level, paragraphLevel, hasStrong)` represents a uniform paragraph without allocating level or paragraph arrays. `levels` optionally contains sorted, disjoint `TextLevel` intervals. Each interval supplies the resolved `level`, an `unwrappedLevel` after UAX #9 L1 with the whole paragraph on one line, and `removed` for X9 characters (including Unicode BN). Both levels default to the analysis level; removal defaults to false. Removed characters remain available to shaping: a discretionary glyph can have nonzero advance without becoming a semantic reordering participant. `paragraphs`, when nonempty, describes every paragraph and ends at context EOF. Paragraph levels are 0 or 1; resolved levels are 0…126. `hasStrong` distinguishes detected directionality from a neutral paragraph's fallback. The engine validates cursors and metadata, rejects non-finite advances and shaping runs that merge across analysis boundaries, and passes immutable analysis to each shaping call.

The engine determines stable inline parts from the unwrapped paragraph, then reorders each candidate line using its shaped levels. Parts separated by foreign content in the unwrapped paragraph stay distinct after that content wraps away. Slice edges follow the inline parent's direction; cloned decorations participate in line fitting, not just painting. Ordinary empty inlines do not become neutral characters, while atomic inlines participate according to their analysis. Out-of-flow anchors do not change sibling reordering. Visual positions are separate from source-node fragment enumeration. Ordinary uniform LTR paragraphs retain the fast path.

Text fragments index `FragmentArena.texts` through `textData`; each `TextFragment` contains original source offsets, the actual font key, resolved bidi level, a provider-owned `shapeKey`, and `TextFragmentKind` (`Glyphs`, `Tab`, or `SegmentBreak`). Tabs and segment breaks retain separate source rectangles rather than coalescing into adjacent glyph runs. Copied fragments keep their shape keys, so a shape key must stay valid until the provider is replaced and `LayoutTree.invalidate()` is called. Font metrics are cached per text style/font within layout; source strings are borrowed, not copied into candidate lines. Normal-whitespace collapsing crosses source/inline boundaries, while segment-break trimming respects inline/text-sequence boundaries, including `contents`. Empty inline descendants follow enclosing margin-edge ownership; standalone characterless siblings use Chrome-compatible preceding-line affinity at existing soft breaks. Verified source-geometry policies and deliberate browser differences are recorded in [SPECIFICATIONS.md](SPECIFICATIONS.md); focused coverage is not a full-conformance claim.

Style dimensions are already parsed/resolved values, not CSS tokens. Percentages are fractions: `Dimension.pct(0.5)` means 50%. Generated `Layout` positions retain normal geometry; each `Fragment.location` is physical-parent-relative, `visualOffset` contains positioning/scroll effects, and `worldLocation` is resolved viewport-relative geometry. `sourceRects(NodeId)` returns an allocation-free iterator over CSSOM-style visual rectangles, joining adjacent shaping pieces of a text font/bidi run on one line while retaining individual paint fragments. `sourceBounds(NodeId)` derives bounds from those rectangles without using them to drive layout; even a zero-height text rectangle retains the whole run's width. Sizes are border-box sizes; `contentSize` is the used content box, not an overflow extent. Layout inputs use CSS pixels without device-pixel rounding.

`Fragment.nonpainting` identifies structural geometry that must not draw its own decoration or content. Interrupted inlines expose nonpainting fragments around lifted block ranges for source rectangles and absolute containing geometry; these have zero `decorationEdges`, `layoutBounds`, and own `scrollableOverflow`. Their existence does not move the lifted blocks or create a line. Phantom continuations containing empty inlines, floats or positioned anchors retain inline-axis geometry without line-height participation; text-only phantom ranges can merge. Cloned decoration does not itself make these lines real, while actual text, preserved whitespace, and authored inline edges retain their normal participation. The CLI serializes this flag.

`Fragment.positioningShell` distinguishes synthetic containing-block ancestry on a later fragmentainer from actual source geometry. These nonpainting carriers preserve clipping and positioning ownership for absolute continuations, but `sourceRects` excludes them. Their inline geometry is resolved against the current frame, including percentage/min/max sizing, margins and flex-item allocations; fixed widths are not scaled with page width. Genuine zero-sized overflow continuations and nonpainting inline interruptions remain source rectangles.

Block `justifySelf` defaults to `Auto`, taking the parent box's `justifyItems` (`Normal` by default). Non-normal positional alignment uses fit-content sizing for an automatic inline size; explicit stretch fills that axis, subject to min/max constraints, including replaced boxes and float-reduced alignment containers. Auto margins take precedence. Flex-item `justifySelf` remains inapplicable. Logical/self/physical alignment and per-property overflow qualifiers are independent of display's inner layout mode.

Cyclic percentage margins, padding, and minimum sizes retain the fixed term of `calc()` during intrinsic contribution measurement. Block and flex contents then resolve against the established inline extent without enlarging it. Flex gaps keep their cyclic zero-percentage basis. Used inline percentage bases remain distinct from semantic flex-main definiteness and automatic block sizes; intrinsic/final flex passes reuse item and line storage.

Orthogonal auto inline sizing observes the containing block's fixed inner constraints, the nearest scrollport's fixed inner size/constraints, and the initial containing block. Block containers use shrink-to-fit sizing; other formatting contexts use the fallback when their available inline space is indefinite. These limits do not make an indefinite containing block definite for percentage resolution. [Writing Modes §7.3.2](https://drafts.csswg.org/css-writing-modes-4/#auto-multicol) permits the selected single-column behavior when multicolumn layout is unsupported.

Leading absolute/fixed inline boxes retain fragment-relative static anchors, even in a zero-height phantom run. Inline-axis self-alignment uses the static containing block's direction, not the bidi paragraph direction. Default/safe absolute alignment uses the specified overflow-limit rectangle rather than immediately falling back at a zero-width anchor; reachable scrolling directions can extend that limit for non-fixed boxes. For bidi insertion, the replaceable analysis service independently resolves a neutral hypothetical anchor; actual text analysis and geometry remain unchanged. CSS2's permitted approximation uses a zero-inline-size stand-in and retains actual surrounding run levels, segmentation, advances, tabs and decorations. Its scratch ordering determines only the anchor coordinate, not a fully reshaped hypothetical paragraph. No source strings are copied, and paragraphs without anchors make no additional analysis calls.

A non-replaced box's ratio-dependent automatic minimum preserves its min-content size, capped by its maximum size ([Sizing 4 §4.3](https://drafts.csswg.org/css-sizing-4/#aspect-ratio-minimum)). An explicit zero minimum opts out; a scrollable axis does not impose this content-based floor. The constraint can break the preferred ratio rather than overflow the content.

## Scroll state and sticky positioning

Set `Tree.viewportScrollOffset` and `Tree.setScrollOffset(id, Point)` with requested physical scroll offsets. Layout clamps requests to the final reachable overflow after positioned layout and scrollbar selection, before scroll/sticky translation. Positive offsets translate contents negatively; negative offsets support reverse scroll origins and reachable alignment overflow. Only computed scrollable axes consume node offsets; boxless and suppressed nodes do not scroll. Input requests are not mutated, so recomputing after content or viewport changes resolves the range again. Sizes and baselines remain box-relative.

Baseline export uses the initial scroll position, not the supplied scroll offset. A non-replaced block-axis scroll container always exports a last baseline at its block-end margin edge, independently of first-baseline availability. Available scroll-container baselines are then clamped to the border edges as required by CSS Align 3.

Sticky positioning resolves each axis against its nearest matching scrollport, including percentage insets, oversized sticky rectangles, nested sticky boxes, and containing-block limits. `Layout.usedMargin` contains placement-resolved margins, including auto margins, separately from collapsed-margin unions. The pinned margin-edge rule and Chrome-compatible interpretation of scrolling containing blocks are detailed in [SPECIFICATIONS.md](SPECIFICATIONS.md).

`Layout.scrollableOverflow` is an unscrolled, border-box-relative rectangle; `LayoutTree.viewportOverflow` uses unscrolled viewport coordinates. These metrics follow actual containing-block ownership, per-axis clipping, normal-flow padding and positioned overflow; viewport-fixed boxes do not enlarge viewport scrolling. Scroll and sticky translations change visual locations without changing these metrics. The JSON adapter exposes `scrollableOverflowX`, `scrollableOverflowY`, `scrollableOverflowWidth`, and `scrollableOverflowHeight` per box, plus the top-level `viewportOverflow` rectangle.

## Scrollbar measurement and layout

`Measure.scrollbars(&mut provider, request)` supplies platform scrollbar geometry. `ScrollbarRequest` carries `width` (`Auto`, `Thin`, `None`), `gutter`, writing mode, direction, and `available`: definite axes describe allotted content space before gutters; indefinite axes request intrinsic sizing. Return finite, nonnegative `ScrollbarMetrics.horizontal` (horizontal scrollbar height) and `.vertical` (vertical scrollbar width), plus `overlay`, `horizontalOnTop`, and `verticalOnLeft`. The host chooses actual thickness and sides, including any small-box clamping; the library does not invent a thin-width ratio or OS convention. `ScrollbarMetrics.zero()` supplies zero-size overlay metrics.

`Style.scrollbarWidth` and `Style.scrollbarGutter` implement `auto`/`thin`/`none` and `auto`/`stable`/`stable both-edges`. Gutters are separate from padding and borders: they enlarge intrinsic sizes but reduce allotted content space in constrained boxes. Absolute containing blocks, percentage bases, sticky scrollports and overflow geometry use the resulting padding/content boxes. Overlay scrollbars reserve no space; `none` suppresses scrollbar UI without disabling scrolling. Replaced boxes use the pinned Overflow 4 non-visible-to-clip rule and acquire no scrollbar gutters.

Each `compute` begins without automatic scrollbar selections, then uses full unscrolled overflow, including positioned descendants, to add newly necessary bars. Geometry-changing selections invalidate intrinsic caches and repeat layout; overlay-only selections need no geometry retry. Selections remain monotone within that call to resolve intrinsic-size feedback, and reset on the next call. `Layout.scrollbarGutter` reports physical reservations; `horizontalScrollbar` and `verticalScrollbar` report selected bars, independently of stable empty gutters.

The JSON adapter exposes `scrollbarGutterTop`, `scrollbarGutterRight`, `scrollbarGutterBottom`, `scrollbarGutterLeft`, `horizontalScrollbar`, and `verticalScrollbar`. Optional root `scrollbars` contains required `auto` and `thin` records, each with numeric `horizontal`/`vertical` and boolean `overlay`/`horizontalOnTop`/`verticalOnLeft`. Omission uses zero-size overlay metrics. This synthetic host caps thickness to definite allotted content space and splits that allowance between mirrored inline gutters; that clamping policy is not imposed by the library.

The Chrome oracle records [CDP content-box quads](https://chromedevtools.github.io/devtools-protocol/tot/DOM/#method-getBoxModel), retaining fractional coordinates rather than subtracting rounded CSSOM client sizes. Unrepresentable host thicknesses/sides, custom thin or overlay policies, and inconsistent tiny mirrored geometry remain explicit unsupported results. Spec/Chrome disagreements remain failures, not exclusions; see [SPECIFICATIONS.md](SPECIFICATIONS.md).

## Native adapter

Each `compute` call starts an independent formatting context under the supplied horizontal-tb, left-to-right viewport. This is a layout-subtree boundary, not an HTML `documentElement`; the browser adapter explicitly creates the same boundary. Root percentage edges use that containing block's inline dimension, not the root's own writing mode. Measurement providers must return consistent metrics for an identical key/request during a call. Size results can survive into the next call of the same `LayoutTree`; see [Incremental layout](#incremental-layout).

One JSON request on stdin produces one JSON result on stdout. Parent indices precede children; node zero has `parent: null`. Subtrees need not occupy contiguous index ranges. Layout and positioned static references follow the tree's sibling order, not arena allocation order, including descendants of `display: contents`.

Schema version 3 separates source-indexed `sources`, generated-box-indexed `boxes`, fragment-indexed `fragments`, the text-metadata arena `texts`, and `viewportOverflow`. Source records distinguish `element` and `text`, exposing visual `x/y/width/height`, `firstBox`, and world-coordinate `rects`; `x/y` use the nearest source ancestor with generated boxes. Single-box used metrics are omitted for non-atomic or fragmented inlines rather than inventing one content box. Generated boxes expose formatting ancestry and continuation links; fragments expose physical ancestry, normal/visual/world geometry, content/padding/overflow rectangles, baseline availability, decoration edges, and optional `textData`. Spec fixtures assert `expected.sources`; the old source-indexed `boxes` and unused content-key/range fields are removed.

Canonical boxes and fragments expose `firstBaselines`/`lastBaselines` objects. Source `firstBaseline`/`lastBaseline` values are projections for that box's writing mode, not the canonical baseline representation. The CLI's opaque measurement fixtures retain scalar baseline inputs and generate coincident tables for their synthetic zero-font content; real measurement providers return full sets.

```json
{"viewport":{"width":800,"height":600},"nodes":[
  {"parent":null,"style":{"display":"block flex","width":200}},
  {"parent":0,"style":{"flexGrow":1},"measure":{"minWidth":20,"maxWidth":80,"height":18}}
]}
```

Dimensions accept pixel numbers, keywords, `{"percent":0.5}` and `{"length":10,"percent":0.5}`. Edge shorthands accept a uniform dimension or named sides. Each alignment property has its own `...Safety` qualifier (`default`, `safe`, `unsafe`). Unknown fields and malformed tree input fail with a nonzero exit status. Measurement fixtures are deterministic test services, not a font shaper.

**Grid phase 2 API:** `display` accepts `"grid"`, `"block grid"`, `"inline-grid"`, and `"inline grid"`. Numeric lines/spans, fixed and definite-percentage tracks, definite-space `fr`, gaps, and `start`/`end`/`center`/`stretch` self-alignment drive layout. Items use their grid areas as containing blocks. Full intrinsic sizing, named placement, areas/repeat expansion, implicit track-list cycling, `order`, occupancy-aware auto-flow, content alignment and baselines remain incomplete; still-auto positions retain the source-order one-column fallback. Structured values for later phases are accepted and stored, not fully implemented. Grid containers remain monolithic during fragmentation; internal grid breaks and subgrid are not implemented. This is not full CSS Grid support.

The grid adapter accepts only parsed longhands, not CSS track-list strings or shorthands:

| JSON style field | Accepted value | Default |
|---|---|---|
| `gridTemplateRows`, `gridTemplateColumns` | `"none"` or a nonempty array of track entries, line-name entries and repeat entries | `"none"` |
| `gridAutoRows`, `gridAutoColumns` | One track size or a nonempty array of track sizes; no names/repeat | `"auto"` |
| `gridTemplateAreas` | Rectangular array of nonempty rows of cell-name strings; `"."` marks an empty cell, `[]` clears the template; every named area must form a rectangle | `[]` |
| `gridAutoFlow` | `"row"`, `"column"`, `"row dense"`, `"column dense"` | `"row"` |
| `gridRowStart`, `gridRowEnd`, `gridColumnStart`, `gridColumnEnd` | `"auto"`, nonzero integer, identifier, `{"line":-2,"name":"edge"}`, or `{"span":2,"name":"edge"}`; `name` is optional | `"auto"` |

A track size is a nonnegative pixel number, `{"percent":0.5}`, `{"length":10,"percent":0.5}`, `"auto"`, `"min-content"`, `"max-content"`, `{"fr":1}`, `{"minmax":[20,{"fr":1}]}`, or `{"fitContent":{"percent":0.5}}`. `minmax` has exactly two breadths: its minimum cannot be flexible; neither breadth is itself `minmax` or `fitContent`. `fitContent` takes a length/percentage. Numeric values must be finite; flex factors and direct length/percentage sizes must be nonnegative. A `calc` dimension may have signed coefficients; its resolved size is range-clamped during track sizing, not while parsing coefficients.

A template line-name entry `{"names":["edge","content-start"]}` names the current line without adding a track; consecutive name entries share that line. A repeat entry is `{"repeat":{"count":3,"tracks":[20,{"names":["cell"]}]}}`; its count is a positive integer, `"auto-fill"`, or `"auto-fit"`. Repeat blocks cannot nest and must contain at least one track. At most one automatic repeat is allowed per axis; its tracks and surrounding tracks must satisfy Grid's fixed-size grammar. Expanded integer repeats and explicit definitions are limited to **10,000 tracks per axis**. Placement line magnitudes and positive span counts are clamped to 10,000; zero lines and nonpositive spans are invalid.

Line names are decoded CSS identifiers, not CSS escape-token strings: a letter, underscore or non-ASCII character may start a name; a leading hyphen must be followed by one of those or another hyphen; later characters may also be digits/hyphens. CSS-wide keywords, `default`, `auto`, and `span` are reserved case-insensitively; `none` is a valid line name. Area cell names follow Grid §7.3's name-code-point grammar instead, allowing initial digits and keywords such as `auto`. Unknown fields, nonrectangular areas, invalid repeat/minmax forms, raw CSS grid strings, grid shorthands and `"subgrid"` are rejected rather than partially interpreted.

In the native API, `Style.grid` is a compact Tree-managed handle into `Tree.grids`, not inline variable-length data or a transferable handle for newly appended nodes. `Tree.setGrid(node, move template)` installs a `GridTemplate` and invalidates layout; `Tree.internGridName(name)` supplies line identifiers and `Tree.internGridAreaName(name)` supplies cell names into the shared `Tree.gridNames` table. Native `Tree.setStyle` preserves the node's grid data; install `GridTemplate.make()` through `setGrid` to clear it. In contrast, a CLI update replaces the whole style, so omitted grid fields reset to their defaults. The Chrome oracle serializes these structured longhands and records requested/specified/computed values plus `CSS.supports` evidence; computed template tracks can be used pixel sizes rather than the authored `fr`/`repeat` notation.

A source text node is `{"parent":0,"text":"words here"}`; it has no `style`, measurement, natural resource, or scroll fields. The adapter's text service supports ASCII letters/digits/spaces, preserved tabs and segment breaks, and all twelve Unicode `Bidi_Control` characters in horizontal-tb LTR and RTL paragraphs. Authored glyph advances are half the supplied font size; the engine positions tabs from measured font metrics. Justification expands eligible word separators without expanding trailing hanging spaces. Bounded UAX #9 analysis handles multiple paragraphs, CSS scopes spanning breaks, isolates, overrides, explicit-level overflow, original-class paragraph direction, and line-end level resets. Unsupported characters, writing modes, and hyphenation fail explicitly. This deterministic profile is not a Unicode font backend. The replaceable analysis/shaping contract also supports repertoire and discretionary glyphs beyond this fixture profile.

For source-text comparisons, `scripts/fixture-font.py` generates original MIT-licensed ASCII outlines with the supplied metrics and half-em advances. No existing font or WPT glyphs are incorporated. Chrome loads the resulting real fonts before layout; the report records byte hashes, DOM Range advances, ascent/descent, normal line height, and alignment-metric evidence. Only exercised matching profiles are compared. Unrepresentable metrics or unmatched script offsets remain unsupported; missing font tooling is an error, not a fallback to platform fonts. Geometry disagreements remain failures.

Inline-style input includes `lineHeight` (`"normal"`, a nonnegative unitless number, or `{"length":20}`), `verticalAlign` (CSS keywords or a length/percentage dimension), `baselineSource`, `textAlign`, `textAlignLast`, `textJustify`, `textWrap`, `whiteSpaceCollapse`, `tabSize`, and `boxDecorationBreak`. `textJustify` accepts auto, none, inter-word, and inter-character; the specification-required legacy value distribute computes to inter-character. `whiteSpaceCollapse` accepts collapse, discard, preserve, preserve-breaks, preserve-spaces, and break-spaces. `tabSize` accepts a nonnegative number or `{"length":20}`; there is no `whiteSpace` shorthand. Optional root `fonts` supplies font-metric records at keys 1…N, selected with `style.fontKey`; key 0 is the fixture's zero-size font. Font records contain `fontSize`, `ascent`, `descent`, `lineGap`, `xHeight`, `capHeight`, `subscriptOffset`, `superscriptOffset`, and `baselines.{alphabetic,ideographic,central,mathematical}`. The fixture service derives x-middle from alphabetic minus half x-height, text-over from zero, and text-under from ascent plus descent. Its measured space/zero advances are half-em, matching the original fixture font; the library imposes no such ratio. Arbitrary nonzero fixture fonts are not assumed representable by Chrome.

`textIndent` accepts a signed finite pixel number, `{"percent":0.2}`, or `{"length":10,"percent":0.2}`. Add selection flags with `{"value":10,"hanging":true,"eachLine":true}`; `value` is required and either flag may be omitted. Keywords such as `auto`, non-boolean flags, and unknown fields are rejected. The Chrome report retains the requested and computed indentation, including keyword-support evidence.

`breakBefore` and `breakAfter` accept auto, avoid, always, all, avoid-page, page, left, right, recto, verso, avoid-column, column, avoid-region, and region. `always` advances the leaf context; a typed force targets the nearest matching context; `all` crosses the outermost context, including when kinds repeat. Combined forces retain the latest page-side requirement. `breakInside` accepts auto, avoid, avoid-page, avoid-column, and avoid-region. All three default to auto. `orphans` and `widows` require positive integral values and default to 2; anonymous boxes inherit those line counts. These are computed style values. `compute` remains continuous-media layout: break controls alone do not create a fragmentation context.

`computeFragmented(tree, output, measurer, viewport, frames)` lays out into host-supplied `Fragmentainers`. `rects` is an optional borrowed slice of physical `Rect` values; an absent/empty sequence cannot satisfy a fragmented request. `repeatStep: Option<Point>` optionally repeats the last rectangle, translated by that step. The host supplies context kind (`Column`, `Page`, `Region`), writing mode, direction, first-page side and recto side. Exhausted finite geometry returns `FragmentationError`, rather than silently dropping content. Page origins are presentation coordinates, not distances added to continuous-flow containing blocks.

Optional borrowed `contexts: Option<&[FragmentainerKind]>` lists outer-to-inner contexts, excluding the leaf `kind`. `ancestors: Option<&[FragmentAncestor]>` supplies row-major `{index, rect}` entries: one per outer context per leaf rectangle. Ordinals begin at zero and stay unchanged or advance by one; advancing an ancestor advances every descendant ordinal. A stable identity keeps identical geometry. Repeated kinds and child rectangles overflowing ancestor bounds are valid. Repeating the last leaf translates every ancestor by `repeatStep` and advances every ancestor ordinal once per repetition.

The nearest Page context supplies page parity and the page area for unanchored fixed positioning. Fixed boxes repeat once per such page identity, not once per column. Choosing the nearest Page in an arbitrary Page→Page host stack is an explicit host API policy; CSS does not define that stack's ownership.

The CLI selects this entrypoint when the root request contains `fragmentation`:

```json
{"viewport":{"width":100,"height":100},
 "fragmentation":{"kind":"column","frames":[{"x":0,"y":0,"width":100,"height":50}],
                  "repeatStep":{"x":120,"y":0}},
 "nodes":[{"parent":null,"style":{"height":120}}]}
```

`frames` must be nonempty; dimensions must be finite and nonnegative. Optional `writingMode` and `direction` default to horizontal-tb and ltr. `firstPage` and `recto` accept left/right, both defaulting to right. The engine resumes block children, paragraph cursors and flex lines/items against each actual frame, preserving full sizing bases and fractional size progress. Widow lookahead uses actual future ancestor/float geometry. Normal box extent and descendant overflow progress are separate. Absolute descendants can continue into further frames; page-fixed contents repeat without internal fragmentation. Frame geometry is supplied externally; this API does not construct CSS columns, page margin boxes, or named regions.

For nested contexts, JSON adds both `"contexts":["page",...]` and `"ancestors":[[{"index":0,"x":0,"y":0,"width":200,"height":300},...],...]`; each ancestry row corresponds to one `frames` entry. The same fixed context stack and writing mode govern the supplied leaf sequence.

`marginBreak` accepts the non-inherited single keyword auto, keep, or discard; its default is auto. It controls adjoining block-axis margins in fragmented layout and is inactive in `compute`. Keep preserves existing margins, including cloned edges, but does not invent slice-continuation margins. Kept trailing margins remain on their originating fixed frame and may overflow its flow footprint; they do not resize host frames or create margin-only continuations. Mixed collapsed policies retain their signed extrema independently. Where the specification does not define adjacency through alignment or unused CSS extent, the engine uses the retained content envelope before trimming. Full ending decorations and taller contained floats can separate inherited context endpoints; an actually selected child break is replayed and pinned so margin removal cannot pull later content backward. This is an explicit adjacency policy, not a claim that physical contact with a fragmentainer edge is normative.

The Chrome adapter compares representable uniform column contexts with real multicol layout and always checks fragment rectangles. Arbitrary nested stacks, variable frame sizes, page contexts and region contexts remain explicit unsupported Chrome adapters; their native specification fixtures still run. Separate direct-browser controls cover repeated-kind nested columns. Chrome's unsupported `margin-break:keep/discard` declarations are reported with requested/computed/support evidence; the default Auto behavior remains comparable. Passing this focused corpus is not a claim of complete fragmentation conformance.

The request accepts optional root `"viewportScrollOffset":{"x":20,"y":30}` and node `"scrollOffset":{"x":20,"y":30}` objects. Both coordinates are required, finite and signed. The browser oracle uses an explicit viewport host, assigns requests after resource loading, and records requested, axis-enabled and actual state. Range clamping is expected; differences in resulting geometry, including browser offset quantization, remain comparison failures rather than unsupported exclusions.

A node may instead contain `"natural":{"width":100,"height":50,"aspectRatio":2}`. Each member is optional, including the ratio; the engine does not infer a ratio merely from two natural dimensions. This attachment makes the node replaced. Content measurements and natural-resource measurements are mutually exclusive and attach only to leaves. `aspectRatio` specifies a CSS preferred ratio; `aspectRatioAuto: true` selects a natural ratio when present, otherwise the specified fallback. Natural ratios use the content box; an explicit ratio follows `boxSizing`.

The browser oracle uses decoded, self-contained SVG images for natural resources. SVG cannot represent every independently supplied intrinsic triple: two positive absolute dimensions imply their ratio. Unrepresentable triples remain explicitly unsupported, not approximated with a text box.

The synthetic baseline marker represents horizontal-tb only. Supplied vertical or sideways baselines, variable intrinsic measurements and distinct first/last line baselines are explicitly unsupported by this browser adapter; they are not fabricated from the requested values.

## Conformance and performance

After building, substitute the emitted executable path for `$CLI`:

```sh
node scripts/chrome-diff.mjs --cli "$CLI" --mode spec
node scripts/chrome-diff.mjs --cli "$CLI" --fuzz 200 --seed 7351
python3 scripts/bench.py --cli "$CLI"
```

Spec fixtures carry normative URLs and authored expected geometry. Every supplied assertion, including `rects`, is checked regardless of feature labels. The `inline-fragments` label only opts browser comparisons into rectangle-by-rectangle matching. Browser runs use the installed Chrome (or `--chrome PATH`); `--chrome-version Chrome/VERSION` rejects a different version. Failures and reduced inputs stay under ignored `.cache/chrome-diff/`. Unsupported oracle adapters are reported and exit nonzero, not counted as passes. Differential/fuzz runs are not a PR gate.

Benchmarks cover block stacks, growing/wrapping flex items, nested containers and measured leaves. They check output geometry before reporting end-to-end median wall time, including process startup and JSON I/O. `--record` explicitly writes the baseline; wall time is not an instruction-count or browser-performance comparison.

`scripts/bench-compare` measures layout time against [taffy](https://github.com/DioxusLabs/taffy) (Rust, pinned crates.io release) and [yoga](https://github.com/facebook/yoga) (C++, pinned commit) on the shared workloads in `bench/compare/workloads.py`: random deep flex trees, block stacks, growing and wrapping flex lines, a nested chain, measured leaves, and a card feed. Every harness reads the same document, times only `compute` (no process startup, JSON or tree construction), and dumps absolute border boxes, which the script compares at 0.05 px. Taffy and yoga rebuild their tree for every iteration so their caches never help. Yoga has no block layout, so its harness models block containers as non-shrinking columns, and it has no CSS automatic minimum size, so random flex trees differ from it by design. The CLI's root `"benchmark":{"iterations":N}` field repeats `compute` and prints the per-call nanoseconds on stderr. `scripts/bench-compare --updates` compares re-layout after small updates instead (`bench/compare/updates.py`): every engine keeps one tree and its caches while a leaf or a container toggles its padding, or the viewport narrows a pixel per step. The comparison needs cargo, cmake and a C++20 compiler and is not a PR gate.

`scripts/bench-updates.py` times re-layout after small edits: an unchanged recompute, one style change on a leaf or a container, a text edit, and a viewport resize, on the ASCII scenes in `bench/updates/workloads.py`. The CLI's root `"updates":{"iterations":N,"cycle":[steps]}` field applies one step before each timed `compute`; a step may replace the `viewport` and `set` a node's whole `style`, a text node's `text` or an element's `scrollOffset` (`Tree.setStyle`, `Tree.setText`, `Tree.setScrollOffset`). Benchmark output reports the average work per compute: passes, full layouts, size probes, cache hits (`LayoutTree.stats`) and provider measure/analyze/shape calls. The script also checks that the geometry after the updates equals a fresh layout of the final document, so `scripts/check` runs it with two iterations as a cache-correctness gate.

Compiler workarounds are recorded in [LIMITATIONS.md](LIMITATIONS.md). No compiler or stdlib patches are vendored.
